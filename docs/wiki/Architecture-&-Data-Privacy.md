# 🔒 Architecture & Data Privacy

## Privacy-First Architecture

Hermes Token Usage Ledger is engineered from the ground up to respect data sovereignty and user privacy:

1. **Zero External Network Requests**: The collector and plugin make **zero outbound HTTP/HTTPS calls**. No telemetry, no usage analytics, no error tracking.
2. **SQLite Read-Only Protection**: The background collector connects to Hermes profile databases using SQLite URI `mode=ro` and executes `PRAGMA query_only=ON`. It is physically impossible for the collector to modify, corrupt, or lock your Hermes profile data.
3. **No Prompt or Credential Inspection**: The plugin tracks only token counts and metadata numbers. Prompts, assistant responses, API keys, and sensitive authorization headers are never read or stored.
4. **Sanitized Endpoint Displays**: If a custom provider URL contains embedded credentials or tokens (e.g., `https://user:pass@api.custom.com`), display routines sanitize and render only the clean origin (`https://api.custom.com`).

## Canonical Token Accounting

- **Input Tokens**: Uncached prompt tokens passed to the LLM.
- **Output Tokens**: Response tokens generated by the model.
- **Cache Read Tokens**: Tokens served directly from prompt cache.
- **Cache Write Tokens**: Tokens written into prompt cache.
- **Reasoning Tokens**: Output tokens consumed by reasoning/thinking models (e.g., DeepSeek R1, Qwen Thinking). **Note**: Reasoning tokens are a subset of Output tokens and are explicitly excluded from total token sums to prevent double-counting.
- **Total Canonical Tokens**: Calculated strictly as:
  $$\text{Total} = \text{Input} + \text{Output} + \text{Cache Read} + \text{Cache Write}$$
